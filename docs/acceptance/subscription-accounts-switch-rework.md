## 模型残留：原因与修复

Claude Code 2.1.323 的恢复流程不是仅从 settings 取默认模型。固定客户端的 `Bb/Bpn` 先选择显式模型、环境变量和 settings 的基础值；随后 `L7e/W/H7e` 可以根据最后一条有效 assistant 的 `inPlaceOfModel/message.model` 和最近的 `attachment.type=model` 身份重新恢复模型。普通 settings 默认值不能可靠地阻止这一步。

`L7e` 的短路条件包括显式会话模型、`ANTHROPIC_MODEL` 与各档默认模型环境变量。订阅启动本来就显式带前缀模型并注入各档映射，因此切入订阅会覆盖官方模型。官方卡片的 model 为空时，旧流程省略了 `--model`，会让已保存的订阅模型再次恢复。源码证据为 `output/model-switch-rework/resume-module.js`、`model-module.js` 与 `restore-priority-evidence.json`，均取自本机固定客户端，未修改客户端二进制。

修复包含两条已有入口的处理：

- 从订阅切到非订阅卡片，卡片有具体模型就按卡片模型启动；卡片使用 CLI 默认值且上一绑定模型为 `matou-*` 时，仅在当次切换启动中显式带 `--model default`，既有绑定仍保留卡片的空 model。让当前 Claude 自己选择官方默认值，不把 Opus 5.5 写死在产品代码里。
- 对本轮已经污染、但官方绑定中 model 为空的旧会话，最终 PTY 启动前从该会话历史尾部只读识别 Matou 模型/身份，必要时同样显式带 `default`。从后向前按块读取，不改历史、用户 settings 或账号凭据；普通官方模型继续沿用原生恢复。已有非订阅绑定若残留 Matou 模型，则先回到该卡片模型。

## Default 的 [1m]：已消除

ChatGPT 别名生成函数没有追加 `[1m]`。固定客户端 `zg → Fg(FS()) → yvt/pu` 按 Opus 能力推导 opt-in 长上下文，对自定义别名也会自动追加。原生 SDK 读回重现了 Default 的 `matou-chatgpt/matou-opus[1m]`，而传入的主模型没有后缀。

当全部三档窗口已知、最小窗口小于 1M 时，订阅投影现在将原生 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 放进当前进程环境及临时 settings.env。保留原有最小窗口和 autoCompactWindow；1M 卡片不加此开关。没有修改固定客户端或压缩实现。

真实 272K 原生读回结果：

- Default resolvedModel 为 `matou-chatgpt/matou-opus`，不带 `[1m]`。
- `get_context_usage.maxTokens/rawMaxTokens = 272000`，`autocompactSource = settings`，`autoCompactThreshold = 239000`，自动压缩开启。
- 真实原生终端菜单只有 Default、Opus、Sonnet、Haiku；三档描述为 272K，菜单和当前模型都没有 `1M context`。

证据：`priority-results.json`（原始读回）、`disable-1m-results.json`（开关读回）与 `native-tui-evidence.json`（生产投影的终端菜单）。阈值是原生运行状态读回，没有发送 239K token 压力请求。

## 耗时拆解与优化

历史 25 秒的现场没有逐阶段时间戳，本轮不把它硬拆成未经记录的数值。下列是同机本轮实测，原生版本和上游均隔离固定。

| 阶段 | 本轮实测与处理 |
| --- | --- |
| 登录 shell 代理解析 | 同机冷读 1680.84ms；后台派发 2.43ms；缓存读取 0.05ms；缓存后完整代理决策 0.47ms。此前约 8 秒的单次值本轮没有重现。runtime 入口现已立即后台预取，首个路由启动复用同一 in-flight/result 缓存 |
| 冷路由启动 | 本轮样本完整冷 acquire 为 569.10–1606.38ms，最终独立样本首次 bootstrap 为 638.54ms。主进程启动调用本身 2.74–25.21ms，完整 acquire 还包括目录/配置/端口与管理就绪 |
| 凭据就绪 | 未 active 时仍保留原有定向采用等待；已 active 的精确凭据列表结果直接使用，不再重复 GET 一次。最终温热样本每轮每次读取约 117–122ms（包含测试记录转发层） |
| 别名和前缀 | 原来每次 prepare 都无条件 PUT aliases、PATCH prefix；一次激活又会 prepare 两次。现在 aliases 与已注册 models 并行读取，只有不一致才写。v8 凭据列表不公开 prefix，因此用实际发布的带前缀模型 ID 核实采用结果 |
| 别名等待 | 保留“未就绪才轮询”的 50ms 间隔；预热样本均首次读取就绪，零额外轮询延时，零别名/前缀写入。原实现也不是每次固定睡 8 秒，8 秒是失败截止时间 |
| Claude Code 启动 | 单独记录 RPC 返回后的原生 initialize 时间；最终独立隔离基准为约 0.31–0.56 秒。真实交互终端另测到约 2.4–3.2 秒的启动，原问题的未修复恢复探针为 4.5 秒；这些不是同一就绪判据，不混算 |

预热的一次 prepare 从 5 个串行本地管理请求缩减为 1 次凭据读取加 2 次并行读取；仍在激活前和最终进程边界各核实一次，保留原有失败保护，不新增长期缓存、存储或运行时 LLM 步骤。

### 同机隔离切换对比

完整生产 RuntimeServer RPC、固定路由与原生 Claude，假上游立即响应，保持设置页路由租约。总耗时从切换请求开始，到新原生进程可接受 SDK initialize；另记录产品激活 RPC 时间与原生后续启动时间。每轮都实际提问验证模型和身份，不把仅创建 PTY 当作模型就绪。

| 轮次 | API Key 总耗时 | 订阅总耗时 | 订阅额外耗时 | 激活 RPC 本身额外耗时 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 655ms | 1133ms | 477ms | 461ms |
| 2 | 625ms | 1354ms | 729ms | 546ms |
| 3 | 606ms | 1060ms | 455ms | 477ms |

最终独立隔离基准三轮均满足额外不超过 1 秒，最大 729ms。证据：`switch-final-one-shot.json`。此前另一轮三组额外为 -576/481/949ms，保留在 `switch-final.json`，不将首轮 API Key 初始化较慢带来的负差值解释为订阅天然更快。

**负载边界仍需说明：**统一 20 文件并发回归期间也记录了同一测试，激活 RPC 的额外耗时为 760/749/977ms，但包含 Claude 原生启动的总差值为 1144/1643/2654ms，未在该高并发测试负载下稳定满足 1 秒。主要差值来自原生初始化波动，不把这一轮隐藏成通过的性能样本。证据：`switch-regression.json`。随后用户已在真实开发版复核“切回官方 / 切到订阅”，两次均在 1 秒以内，通过本关；高并发测试的负载边界仍保留。

## 本轮自行决定

1. 官方默认值交给当前 CLI 的 `default` 选择，不固定版本；只对 Matou 订阅模型残留改变恢复行为。
2. 在既有切换入口和最终进程入口闭合新切换及旧污染恢复；当次 default 重置不持久化，避免覆盖用户后来的原生 /model 选择。不增加存储字段或修改用户历史。
3. 使用验证过的原生开关去掉 1M 误导，保留 272K 原生压缩窗口；不把可修问题留作已知问题。
4. 保留两次启动检查，只消除重复请求和无意义写入；不引入共享准备结果的跨会话生命周期。
5. 以隔离性能样本为主要基准，同时保留并发回归下的端到端超标，实际开发版由用户下一次重启复核。
