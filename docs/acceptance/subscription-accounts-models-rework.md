## 用户现在会得到什么

1. ChatGPT 的模型响应即使带有很长的指令字段，只要模型正文不超过 **4MiB** 就能读取；投影给界面的仍只有 ID、显示名、来源、窗口和输出上限，长指令不会进入渲染层。
2. 账号模型列表读取失败时，使用当前路由的 `/routing/model-definitions/codex` 返回值作为候选，过滤 image/video、codex-auto-review 等非对话模型。正常读到账号模型时仍取它与路由模型的交集。没有硬写另一份模型目录。
3. 如果最终仍无候选，不显示三个空下拉：显示「没有读到可用的模型」/「No available models were found」和「重试」，「保存」「保存并切换」均禁用。重读失败时空状态文案继续保留，并在同一框里说明原因；仍可再次重试。
4. 重试只重新读取模型，保留已填名称、有效映射和当前草稿；不重新 OAuth、不取消草稿、不刷新额度、不自动保存或切换。既支持当前登录草稿，也支持编辑已保存卡片。

## 大小限制与模型来源

- `account-readers.ts`：模型正文单独为 4MiB；额度、账号资格等仍为 **256KiB**。模型解析前后的两次大小检查均使用模型上限，UTF-8 字节数也受限。
- `management-client.ts`：原传输上限是 1MiB。模型 api-call 是「JSON 包装 JSON 字符串」，为转义后的包装预留最多 `4MiB × 2 + 64KiB`；解包后仍严格限制模型正文 4MiB。普通管理响应继续原 1MiB 传输限制，小账号响应解包仍是 256KiB。路由模型定义和凭据模型列表的传输上限为 4MiB。
- Codex 候选的显示名、窗口、输出上限来自路由 model-definitions；账号接口里的不同名称或数值不覆盖它。账号读取失败时使用同一来源兜底，不把候选当成已经验证的真实推理权限。
- 新增 `provider-config.subscription.models-read`：`{attemptId}` 或 `{providerId}` 恰好一个，返回精简的 `SubscriptionAccountDetails`。草稿读取校验当前连接归属，完成后只更新模型和内存草稿；租约总会释放，现有只读存储门禁保持。

## 我自己做的决定

1. 模型正文与小账号正文分开设限，管理客户端为模型包装预留转义空间，避免只修解析器却仍被传输层挡住。
2. 模型重读复用当前凭据和已有账号/额度快照，新增单一受控 RPC，不复用“重新登录”或重复额度读取来重试。
3. Codex 元数据以路由定义为准；显示名沿用实际原文，默认选择用 ID，避免测试和 UI 人工改名。
4. 来自 DSH：空状态复用现有样式，保留两个禁用保存按钮；模型过滤在既有设置 helper 中统一使用；busy 锁防重复；重读成功只更新映射基线、不抹掉用户名称的未保存状态；重读失败时保留指定空文案并在同框追加原因。

没有新增依赖、持久存储或运行时 LLM 步骤。自动兜底使用原本就已并发读取的路由定义，不增加一次服务方请求；用户主动重试只触发一次模型发现读取与本地模型定义读取，没有模型推理费用或额度轮询。
