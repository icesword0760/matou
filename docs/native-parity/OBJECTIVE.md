在独立分支与独立工作区中，使用 Rust＋GPUI＋libghostty-vt，完成现有 Matou 的原生等价实现。覆盖 macOS 与 Windows，先实现并验收 macOS，再完成 Windows。

本任务的核心目标是：在功能逻辑、交互效果和 UI 样式达到现有 Matou 1:1 还原的前提下，完成原生技术迁移。 不重新设计产品，不自行增删能力，不通过简化现有行为换取实现便利。

以下条款构成本 goal 的完整范围、执行护栏与完成标准。

1．最终目标与完成定义

最终交付能够独立安装、运行的 macOS 和 Windows 原生 Matou，以及可复现的对照验收证据。

三个维度必须同时成立：
- 功能逻辑一致：相同初始数据、用户操作和外部事件，产生相同业务结果、状态迁移、持久化结果及异常恢复行为。
- 交互效果一致：入口、操作步骤、反馈时机、焦点、键盘鼠标操作、拖拽、滚动、动画和窗口行为一致。
- UI 样式一致：同平台、同窗口尺寸、同 DPI、同字体、同主题、同数据状态下，应用绘制区域达到像素级对齐。
不得用单终端原型、部分功能完成、编译通过、截图近似、Mac 阶段完成或性能改善，替代整个目标完成。

2．冻结现有 Matou 基线

正式实现前，先建立稳定、可运行、可重复取证的对照基线：
1. 核对现有安装包、源码提交、未提交改动与真实运行行为，记录对应关系。无法对应时先明确差异，不随意选择方便的版本。
2. 使用隔离数据运行参考 Matou，保留整个任务期间可重复操作的对照环境；不得修改参考应用来迎合新实现。
3. 从实际界面入口、源码调用链、已有文档和测试盘点范围。实际产品行为是主要证据，文档与测试辅助发现遗漏。
4. 主线后续变化登记为候选增量，不自动追随。更新冻结基线须明确变更范围与需要重做的验收。
5. 既有行为与文档冲突、明显缺陷或数据安全要求冲突时，记录具体场景。实质产品取舍提交用户裁决，只阻塞相关部分，其余工作继续。
本次对照对象是现有 Matou 整个产品。 过去针对外部 reference product 的“只比较 CLI 黑色区域”规则，不得用于缩小本次范围。

盘点至少覆盖：
- 工作区、事项、场景、会话及现有层级和生命周期。
- 终端、标签、分屏、卡片、会话画布、DAG、分支和 worktree。
- 会话创建、输入输出、恢复、历史、搜索、复制粘贴及关闭重开。
- Agent、账户、模型供应商、预设、登录与配置。
- Git、通知、HUD、快捷操作、设置、语言和主题。
- 多窗口、独立窗口、多显示器、焦点恢复和平台集成。
- CLI、自动化及外部控制入口。
- 存储、故障恢复、打包、安装和更新行为。
该清单只是盘点起点。冻结基线实际存在的能力均属于范围，不能因未列出而自动排除。

3．技术路线与迁移边界
- GPUI 负责应用界面和交互，libghostty-vt 负责终端解析与状态，Rust 负责原生核心及平台适配。
- 最终不得使用 Electron、Chromium、WebView 或隐藏浏览器承载 Matou 自身界面。
- 开发过程中允许临时连接旧运行时，以尽早验证真实界面和行为；必须标记为过渡实现，明确退出条件，不能据此宣称原生迁移完成。
- Matou 自有运行时最终迁至原生实现，不以后台继续启动旧 Electron/Node 运行时作为完成方案。
- 用户运行的第三方 CLI、Agent 和既有外部工具不属于重写范围，其必要依赖不受上一条限制。
- 优先复用现有图标、字体、图片、文案、设计参数、数据格式、协议与行为测试。
- 引擎默认行为与现有 Matou 不一致时，由适配层补齐，不要求用户改变操作习惯。
- 现有原生实验代码逐项审查后复用；实验 UI 不能直接替代正式产品界面。
- 先明确领域状态、存储、PTY、终端、窗口与视图的必要接口，再分工实现；不借迁移建立无实际用途的通用框架。
4．分阶段推进

Windows 优先以现有 Windows Matou 为对照。如果没有可运行基线，列出无法直接取证的平台行为，确定对照规则后实施；不得自行将 Mac 的系统控件和平台行为作为 Windows 的全部标准。

5．采用任务依赖 DAG 并行开发

开发任务 DAG 与产品内的会话 DAG 分别管理。

每个任务节点明确：
- 对应功能与场景编号。
- 已确认的行为、视觉基线与实现方案。
- 前置依赖、输入输出和接口约束。
- 工作区、文件所有权与唯一写入者。
- 最小实现范围、必要验证和完成证据。
- 阻塞条件及交回主代理的条件。
执行规则：
1. 主代理负责排查、方案、接口、依赖排序、整合和最终验收。未明确的问题不能直接交给实现代理自行选择架构。
2. 只并行推进依赖已满足、写入范围不重叠的节点；共享文件指定唯一写入者。
3. 优先推进关键路径，以减少总耗时和返工为目标，不追求代理数量或开工数量。
4. 同时最多两个实现代理，必要时增加一个只读审查代理，并服从宿主并发上限。
5. 模型、供应商、Broker 授权及五栏派活模板沿用当前 AGENTS.md，保留主模型与推理强度。
6. 子代理只执行分配的定点验证；主代理集中组织集成检查和真实 UI 验收。
7. 优先交付能真实操作的纵向功能闭环，不先堆完静态页面再集中接线。
8. 接口冲突、方案不成立或连续两次定点验证失败时，交主代理重新排查，不自行扩大范围或叠加兼容补丁。
6．统一的一致性对照矩阵

建立一份“现有 Matou → 原生 Matou 对照矩阵”，作为范围、任务和验收状态的统一索引：
字段	要求
场景编号	稳定编号，关联实现和证据
基线	参考版本、入口、初始数据、环境
操作	可重复的用户操作或外部事件序列
预期结果	可见反馈、状态迁移、持久化和异常行为
原生实现	模块、任务节点、当前状态
验收证据	对照截图、录屏、测试或数据结果
差异与阻塞	原因、处理方式、尚未完成事项


相关界面覆盖适用的默认、加载、空、悬停、焦点、选中、禁用、错误、恢复状态及操作后的状态变化。

验证按问题分层：
- 逻辑对照：同数据和操作序列，对照业务状态、事件结果与持久化内容。
- 视觉对照：同条件截图叠加与差分，定位布局、字体、颜色、图标和状态差异。
- 交互对照：真实窗口操作及必要录屏，核对焦点、滚动、拖拽、动画和反馈时机。
既有 E2E 场景应迁移为原生验收契约。可以更换自动化驱动，不能因为原生界面没有 DOM 就删除验收项。

不得通过修改预期、扩大遮罩、放宽阈值、删除失败场景或使用 mock 替代真实行为来消除差异。

7．像素级与交互验收

同平台原版与原生版进行比较，不要求 macOS 和 Windows 的系统控件彼此相同。
- 固定逻辑窗口尺寸、DPI、字体、主题、缩放、数据和滚动位置。
- 静态应用区域的布局边界、尺寸、间距、颜色、字体属性、图标、文案和控件状态必须对齐。
- 不得用整张截图的高相似度掩盖局部明显错误。
- 基线阶段重复截取原版自身，识别动态内容和渲染噪声后冻结差分规则，不能看到原生结果后反向放宽标准。
- 时间、闪烁光标等不稳定区域，仅允许使用事先登记的最小遮罩。
- 字体抗锯齿等渲染差异须提供局部证据，不能笼统以技术原因为由豁免。确实无法达到要求时交用户裁决；批准前保持未完成。
- 动画和拖拽须覆盖起点、过程、终点、持续时间、打断及恢复，不能只比较终点。
- 输入法、候选位置、选区、剪贴板、快捷键、焦点、滚动锚点和多窗口切换，必须根据场景在真实应用验证。
“看起来差不多”不构成验收通过。

8．性能、可靠性与数据

性能目标是在保持现有行为和效果的前提下，不引入用户可感知退化，并如实给出原生方案的收益或代价。

正式实现前测量并冻结必要的性能基线与预算：
- 冷热启动和首个可操作画面。
- 输入到显示、会话切换、缩放、滚动及连续拖拽。
- 大历史首次加载、缓存恢复、翻页和搜索。
- 多会话持续输出时的响应、CPU、内存与后台资源占用。
- 关闭重开、崩溃恢复和异常输入下的数据完整性。
使用可重复的操作和负载，记录典型值、尾部延迟及明显卡顿。区分数据准备、绘制回调和真实显示结果，不混用指标。

复用既有真实大日志与明确压力场景。终端验证覆盖现有能力涉及的 Unicode、中文输入法、组合字符、样式、尺寸变化、清屏、备用屏幕、历史和真实交互式 CLI。

不得通过减少历史、丢输出、延迟必要持久化、削减后台行为或取消动画换取性能成绩。

数据兼容、导入、升级中断和恢复均使用副本验证，不使用用户真实数据库做实验。

9．最小等价实现与复杂度约束

本任务只实现冻结基线要求的等价行为。不得自行扩大为更通用、更可扩展或覆盖更多理论场景的产品。

实现规则：
1. 默认选择直接、可维护、能闭合既有场景的最小实现。
2. 现有产品没有的兼容层、配置项、状态、回退、重试、迁移分支和扩展接口，不提前添加。
3. 新增防御逻辑、抽象或依赖，必须有明确依据：既有行为要求、已复现故障，或平台/API 的必要约束。“以后可能需要”“以防万一”“最佳实践”本身不构成依据。
4. 边界检查放在实际接收不可信输入或外部结果的位置。内部已成立的约束直接使用，不在每层重复检查、转换和兜底。
5. 错误在明确责任层处理，不层层吞掉后返回看似成功的默认结果。
6. 没有多个明确的实际使用场景，不为可能复用建立通用框架；不为局部问题引入全局抽象。
7. 必要的资源释放、线程约束、内存安全和数据保护必须满足，优先采用标准机制和最小实现，不自行扩建保护体系。
8. 发现范围外问题先登记，不顺手修复或重构。
9. 审查额外复杂度时，只需指出对应行为、实际问题或平台约束；没有依据则删除或简化，不另建繁重审批和论证流程。
10. 常规取舍由主代理自主处理；只有一致性目标与必要技术约束发生实质冲突时，才提交用户裁决。
10．最小充分验证，禁止无限加码

完整验收是冻结范围全部覆盖，不是穷举所有理论风险。
- 每项测试、检查、快照、日志或报告必须回答：证明哪个对齐要求，或防止哪个已确认回归？回答不出来就不添加。
- 优先复用既有场景与有效证据，不为同一事实堆叠多套等价验证。
- 不编写仅重复实现逻辑的测试。
- 开发阶段做定点验证，稳定后集中做必要的集成、真实界面及打包验收，不每改一个文件就全量运行。
- 源码、依赖、配置、输入未变且无新风险时，不重复已经成功的检查。
- 自动测试、截图和真实操作分别解决不同问题，不机械要求每个修改都完成全套。
- 仓库强制门禁、实际平台差异和明确覆盖缺口仍必须检查。
- 新增验证由新发现的实际行为、已复现缺陷或明确覆盖缺口触发，不持续提高完成门槛。
- 节点通过约定验收后即结束，不继续扩充无关边缘场景。
这些规则限制的是无依据的工作，不能用于跳过明确的一致性验收要求。

11．分支、环境与发布护栏
- 创建独立 codex/… 分支和已核实归属的 worktree；操作前检查现有改动，保留其他任务成果。
- 原生应用使用独立应用身份、数据目录、缓存、日志、端口和测试更新渠道，允许与现有 Matou 同时运行。
- 不覆盖现有安装包，不改真实会话、账户配置、数据库和项目数据。
- 发布与更新能力在隔离环境验证；本 goal 不自动授权合并主线、生产发布或替换当前安装。
- 不关闭系统保护，不暂停系统服务来规避权限或性能问题。
- 正常编码、构建、测试、任务内提交和独立分支集成自主连续推进，不重复询问已授权事项。
- 产品取舍、超出授权的外部行为、生产变更和不可逆操作，按实际权限要求处理。
12．长任务连续性与效率

在项目已有文档体系中维护最少必要记录：
- 目标、冻结基线与已确认决策。
- 对照矩阵及证据索引。
- 任务依赖 DAG 和当前状态。
- 简短交接点：已完成、阻塞、下一步。
避免多份进度文档记录相同内容。

每次续作：
1. 核对真实分支、改动、代理状态、构建和运行版本。
2. 从尚未闭合的关键路径选择下一项工作。
3. 复用有效结果，避免重复排查、重复构建或重复创建代理。
4. 优先解决当前节点差异，避免不断扩展实现而积累验收欠账。
5. 将证据绑定到具体构建和输入；相关变更只使受影响证据失效，不机械重跑全部检查。
6. 明确区分“已修改”“自动验证通过”“真实产品行为已验证”和“尚未验证”。
不得自行缩减平台、降低还原精度、变更技术路线或改成简化产品。遇到阻塞，说明证据、影响、建议及最少必要决策；不受阻工作继续推进。

13．最终完成审计与交付

标记整个 goal 完成前，主代理必须从“尚未证明完成”的立场逐项核对：
- 冻结范围内全部功能和场景有对应实现。
- macOS、Windows 的逻辑、交互与视觉矩阵全部闭合。
- 无未批准差异、未验必需项或仅通过 mock 证明的真实路径。
- 最终交付包经过真实安装、启动、文件访问、核心操作、退出重开和必要故障恢复验证。
- 性能、可靠性与数据完整性达到冻结标准。
- 最终应用不依赖过渡旧运行时或浏览器界面。
- 交付源码分支、构建说明、两平台安装包、验收结果、证据索引与复现步骤。
- 现有 Matou 安装及真实数据未被破坏，未擅自合并或生产发布。
Mac 通过只能标记“Mac 阶段完成”；Windows 未通过时整个 goal 继续有效。任何必需项仍缺失、失败、证据不足或未验证，都不能标记整个目标完成。

执行全过程遵循：先确认基线，按依赖实现，每个节点同步验证一致性；用最小充分实现完成已确定范围，通过验收后及时结束，不自行增加产品能力、工程复杂度或验证门槛。
