# Runtime Robustness Task 5：通知容量与已读保留期报告

日期：2026-09-01

## 用户结果

- 一个工作空间持续产生大量 Agent 消息时，只保留最新 1,000 条，不会挤掉其他工作空间的通知。
- 尚未查看的通知持续保留，超过 30 天也不会仅因时间被删除。
- 已查看通知保留 30 天；之后在下一次通知到达或打开通知中心读取快照时自动清理。
- 没有关联到工作空间的异常通知进入独立队列，同样最多 1,000 条，仍可在通知中心查看。
- 同一恢复过程等使用 `replacementKey` 更新原通知，不会重复占用容量。

## 规则边界

| 场景 | 结果 |
|---|---|
| 单工作空间第 1,001 条通知到达 | 按 `timestamp + id` 确定性删除最旧一条，最新通知立即可见 |
| 另一工作空间仍有通知 | 独立计数，不参与当前工作空间淘汰 |
| 未读通知已存在 30 天以上 | 继续保留，直到用户处理或容量淘汰 |
| 已读通知刚满 30 天 | 继续保留；超过边界后清理 |
| 容量淘汰或用户删除通知 | 同步释放已不存在通知对应的 cooldown key，后续真实事件不会被旧冷却状态误吞 |
| 清空通知中心 | 通知、会话提示与对应 cooldown 状态一起清空 |

## 10,000 条容量基准

使用 Node 22 直接运行真实 `AgentNotificationStore`：

- 10 个工作空间，每个 1,000 条，总计 10,000 条；
- 再向第一个工作空间 push 1 条并执行 prune；
- 本机单次耗时 **0.71 ms**；
- 最终总量仍为 10,000，十个工作空间均为 1,000。

测试使用相对耗时门禁，避免把某台机器的 20 ms 绝对值写成不稳定 CI 断言；本机实测仍低于计划目标。

## Electron 用户路径

真实 Electron 中通过产品 E2E bridge 向两个工作空间 bucket 各注入 1,001 条通知：

1. 当前事项 badge 显示 `99+`；
2. 通知中心显示 2,000 条，而不是 2,002 条；
3. 两个 bucket 的最旧通知均已淘汰；
4. 打开仍然存在的当前会话通知后，回到来源终端，中心剩余 1,999 条；
5. 点击清空后显示 0 和“暂无通知”，事项 badge 消失。

同文件中的既有“Escape 关闭通知中心”场景在当前共享工作树持续失败；其失败发生在通知 Store 之外的键盘事件/焦点交互路径。本 Task 新增容量、导航与清理场景独立复跑通过，该既有交互回归已单独上报主任务统一处理。
